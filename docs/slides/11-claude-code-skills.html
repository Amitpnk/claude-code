Why Skills

General capability isn't specialist output

 

Claude is a general-purpose model. It reasons, writes, and codes across many domains. But there's a gap between general capability and reliable, high-quality output for one specific kind of task — and that gap is where Skills live.

Why Skills

Example: "Generate a PowerPoint"

It knows the domain. It doesn't know your version of it.

What Claude knows

  • What PowerPoint is
  • How to reason about slide structure
  • Which Python library to use

What it doesn't

  • How to handle the layout
  • Which fonts to use
  • How and where to place charts and tables
  • Your company's design guidelines
Why Skills

The same gap shows up everywhere

Any task where "correct in general" and "correct here" are different things.

Frontend development
Knows React. Doesn't know your design system.
02
Data analysis
Knows pandas. Doesn't know which metrics your team trusts.
03
Writing documents
Knows how to write. Doesn't know your house style.
04
Code review
Knows what a bug is. Doesn't know what your team actually blocks on.
Why Skills

"Just write a detailed prompt"

The obvious fix — and why it stops working.
✗

You have to remember it and retype it every single time.

✗

Move it to the system prompt and it burns context tokens in every session — even the ones that don't need it.

✗

You can't bundle resources with a prompt — reference charts, templates, schemas have nowhere to live.

✗

Sharing, versioning and improving a prompt is awkward — possible with extra tooling, but never native.

✗

Prompts don't compose. "Read the PDF, extract the table, then build the deck from it" is three prompts you're stitching by hand.

So — what is a Skill?

 

Skills are reusable, file-based resources that give Claude domain-specific expertise — workflows, context, and best practices that turn a general-purpose agent into a specialist.

✓
Unlike a prompt, it isn't one-off
A prompt is an instruction for a single task. A Skill persists and is reused.
✓
It loads on demand
Say "create a PPT" and only then does Claude find the Skill, read it, and follow it.
✓
No more repeating yourself
The same guidance stops being re-explained across every new conversation.

A Skill is a folder

One required file, and whatever else the job needs.

If the Skill needs executable code, it goes in scripts/. Templates, guidelines and reference material go in templates/ and resources/.

What's inside

SKILL.md is required. Everything else is optional and loaded only when referenced.

How Skills load

Core idea: don't present information until the moment it's needed.
L1
The description — always visible
A single line in the frontmatter. This is all Claude sees until something matches it.
L2
The SKILL.md body — loaded on demand
Read only once the description matches what you asked for.
L3
Referenced resources — loaded if needed
Scripts, templates and reference docs, pulled in only when the body points at them.

Two scopes

Where you put the folder decides who gets it.

Personal Skills

~/.claude/skills
  • Available across all your projects
  • Just yours — not shared with anyone

Project Skills

.claude/skills
  • Available in this project only
  • Committed to the repo — shared with your teammates

Three ways to create one

 
01
By hand
Create the folder and write SKILL.md yourself. Not where beginners should start.
02
Let Claude do it — the skill-creator Skill
Creates new Skills, improves existing ones, and tests how reliably they trigger.
03
Install from the community
Sites like skillsmp.com. Convenient, but read before you install.
Vet anything you install. A Skill is instructions Claude will follow and scripts it may run. github.com/anthropics/skills is the safe, official source.

skill-creator

Type / for skills — or reach for it from the Skills menu.

Skills vs CLAUDE.md

Two different jobs — don't force one to do the other's work.

CLAUDE.md

Always loaded, every session
  • Project facts & conventions
  • Small, constant, under ~200 lines

Skills

Loaded on demand
  • Multi-step procedures & workflows
  • Can be long and detailed — it's not in every session's context

When to reach for a Skill

 
01
A workflow you repeat across many sessions
If you've explained the same procedure three times, it's a Skill now.
02
A multi-step procedure too long for CLAUDE.md
Detailed enough that stuffing it into CLAUDE.md would bloat every session.
03
Something worth sharing
Across your own projects, or with teammates who hit the same problem.
04
A capability that only applies sometimes
Not every session needs it — so it shouldn't cost context in every session.

Anatomy of a good Skill

 
✓
A clear trigger description
Precisely when should Claude reach for this — not a vague topic label.
✓
Step-by-step instructions
The actual procedure, written the way you'd explain it to a new hire.
✓
Examples of correct usage
A concrete example resolves ambiguity a description alone can't.

From one Skill to a library

The steps make one Skill. These turn a folder of them into an asset.
✓
Let the pattern tell you
If you've explained the same procedure three times, that's the signal — don't plan the library up front.
✓
Promote it from personal to project
Prove it in ~/.claude/skills first, then move it to .claude/skills and commit it once it's earned its place.
✓
Watch the triggers, not just the steps
A Skill nobody's Claude reaches for is dead weight. Misfires and misses are description problems.
✓
Update it when the workflow changes
A stale Skill is worse than none — it teaches the old way with full confidence.

Common mistakes

 

Do this

  • One Skill, one job
  • Write a specific, testable trigger description
  • Test a Skill before you share it with the team

Not this

  • Dumping every workflow into one giant catch-all Skill
  • Vague triggers Claude can't reliably match against
  • Skills nobody updates once the workflow changes

Knowledge that compounds

 

Every Skill you write is reusable capital — it pays off in every future project, and every teammate who reaches for it. Next video pairs this with SubAgents, so that reusable capability can run in its own isolated context too.

Key takeaways

 
✓

Skills are invoked on demand, not loaded into every session like CLAUDE.md.

✓

Use CLAUDE.md for constant project facts, Skills for repeated multi-step workflows.

✓

A good Skill has a specific trigger, clear steps, and a concrete example.

✓

Build the library incrementally — notice a pattern, write it, test it, share it.
