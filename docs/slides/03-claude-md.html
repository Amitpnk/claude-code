Why CLAUDE.md?

LLMs don't have memory.
✗

Claude Code can't remember anything from a previous session.

✗

So you end up repeating the same instructions across sessions.

✗

Repeating instructions is cumbersome and error-prone — easy to miss something in the prompt.

✗

That missed detail leads to inconsistent code generation, session to session.

What is CLAUDE.md?

A persistent system prompt for your project.
✓
Special project-level instruction file
Used by Claude Code to guide how it behaves while working on your codebase.
✓
Say it once, not every session
Project structure, coding conventions, how to run/build/test, what tools to use.
✓
Loaded automatically
Claude uses it as context every time — no re-prompting required.

Creating CLAUDE.md

Two ways to get one.
01
Manually
Create the CLAUDE.md file yourself and write the sections you already know matter.
02
Using /init
Let Claude scan the repo and generate a first draft for you.

How /init works

 
01
Triggers an internal agent
It takes over the scanning and writing task.
02
Scans high-signal files first
package.json, requirements.txt, config files, README.md.
03
Reads the directory tree
Builds a picture of the overall structure.
04
Infers stack, layout, naming
Tech stack, folder layout, and naming conventions.
05
Writes CLAUDE.md to project root
With whatever context it inferred.

The generated file is a draft

 

~30% useful out of the box

  • Tech stack
  • Folder layout
  • Naming conventions it could infer

~70% you still have to write

  • Workflows and constraints
  • What to avoid
  • Deployment targets

Content of CLAUDE.md

Six sections, each answering one question.

Project Context

A short description of the project so Claude immediately understands what it's building or modifying.
This is a todo application
for demo that stores
projects and their tasks.

Architecture

Explains how the codebase is structured and where things belong.
- routes live in routers/
- business logic lives in
  services/
- schemas live in schemas/
- persistence logic lives
  in repository/

Code Style

Tells Claude how code should look and what conventions to follow.
- Use Python type hints
  everywhere
- Prefer Pydantic models for
  request/response schemas
- Keep functions small
  and focused

Preferred Libraries

What tools and frameworks should be used.
- Use FastAPI for the API
- Use Pydantic for validation
- Use SQLAlchemy for the ORM
- Do not introduce new deps
  unless necessary

Commands

Exact commands for running, testing, and maintaining the project.
- Install: npm install
- Dev server: npm run dev
- Tests: npm test

Critical Rules

Highlights critical warnings, edge cases, and things to avoid.
- Do not modify database.py
  unless absolutely necessary
- Employee IDs are provided
  by the client — never
  auto-generate UUIDs

Where CLAUDE.md lives

Project-level vs global — same file format, different scope.

More places it can live

 
→

Project root — ./CLAUDE.md. The main file, committed to git.

→

Inside .claude/ — ./.claude/CLAUDE.md. Same effect, keeps the root tidier.

→

Local, personal — CLAUDE.local.md. Read alongside the main file, gitignored automatically, so your personal tweaks never land in the repo.

→

Global — ~/.claude/CLAUDE.md. Personal preferences — coding style, preferred tools, working style — available across every project.

→

Subdirectory — ./some/folder/CLAUDE.md. Starting from the current working directory, Claude Code recurses up to /, reading every CLAUDE.md and CLAUDE.local.md it finds — especially useful in large repos.

Good practices

 
✓

Start with /init, then prune aggressively.

✓

Commit it to git — it's part of the codebase, not personal config.

✓

Only put universally applicable things in it, not one-off exceptions.

✓

Use emphasis sparingly for critical rules — if everything is IMPORTANT, nothing is.

✓

Keep it under ~200 lines. As instruction count rises, instruction-following quality drops uniformly.

✓

The cut test: would removing this line actually cause Claude to make a mistake? If not, cut it.

Split into .claude/rules/

Move stable, scoped guidance out of CLAUDE.md into topic files, loaded on demand.

Reference docs with @imports

Point at documentation that already exists instead of duplicating it inline.
Important

Three techniques that matter most

This is how CLAUDE.md scales without bloating.
01
Split into .claude/rules/
Topic-specific rules, loaded on demand instead of always-on.
02
Use @imports
Reference existing docs instead of duplicating them.
03
Subdirectory CLAUDE.md files
Local context that loads only when Claude is working in that folder.

Treat it as a living document

Build it organically, not upfront.
✓
Grow it from real friction
Add sections as issues actually come up, not speculatively upfront.
✓
Correct once, then codify
The first time you correct Claude on something, write the rule down so you never correct it again.
✓
Audit periodically
Instructions drift out of date as the project changes — review them like stale code.

Auto memory

A persistent memory Claude builds as it works — separate from CLAUDE.md.
✓
Learns as it goes
Discovers something about your project — "this app uses INR, not USD" — and saves it. Next session, it already knows.
✓
Lives per-project
~/.claude/projects/<project>/memory/MEMORY.md — outside the repo, never committed.
✓
Capped and reviewable
Only the first 200 lines load automatically each session. Run /memory anytime to see or edit what's saved.

CLAUDE.md vs Memory

Two files, both acting as memory — one you write, one Claude writes.

CLAUDE.md

  • Written by you
  • Committed to git, shared with the team
  • Loaded every session
  • Universal rules and conventions

MEMORY.md (auto memory)

  • Written by Claude, automatically
  • Lives outside the repo, personal
  • First 200 lines load every session
  • Project-specific learnings and corrections

You can steer memory directly

Auto memory isn't only automatic — you can tell Claude what to remember.
prompt
> update your memory files - we use INR and not USD
Saved to MEMORY.md.
Next session: Claude already knows.

> /memory
Opens MEMORY.md to review or edit what was saved.

Key takeaways

 
✓

Claude Code has no memory across sessions — CLAUDE.md is how you stop repeating yourself.

✓

It's a persistent system prompt: structure, conventions, commands, tools — written once, loaded every time.

✓

/init gives you a fast first draft, but only gets you ~30% of the way there.

✓

Keep it short, universal, and git-committed — split rules and @imports handle the rest as it grows.

✓

Auto memory is the other half — what Claude learns on its own, reviewable anytime with /memory.
